    Task: Lance's conflict rules in the C++ commit path¶

    Status: delegated (implementer: Claude Haiku 5.5, reviewer: Claude Opus 5.5). ROADMAP "Table-format items", T2 (Wave 2). Three sessions: C1 (classify each concurrent pair as Lance does: compatible, retryable, incompatible), C2 (rebase compatible pairs without re-running the operation), C3 (merge deletion vectors of concurrent deletes / updates on the same fragment). Do only the phase you are given.

    Budget about 200k tokens; aim for 120k. Never read a large file whole: grep -n, then sed -n 'A,Bp' windows of at most ~120 lines. Big ones: src/dataset/dataset_ops.cpp (2k+), src/table/dataset_transaction.cpp, src/table/transaction_file.cpp, bindings/python/nanolance/lance/dataset.py (5k+).     1. Goal¶

    When a C++ commit (commit_next_version, src/dataset/dataset.cpp ~line 182) loses the race for its version, nanolance today does one of two things: rebase (same file, ~line 92) succeeds only when the other writers did nothing but add fragments; anything else is a "commit conflict" and the operation's retry_on_conflict wrapper re-runs it from scratch on the new version. Two consequences:

    • Wrong results where Lance refuses. A delete raced by an overwrite is re-run on the new data and succeeds; Lance raises "Incompatible transaction". Same for two update_config calls on one key (last writer wins silently).
    • Needless work where Lance rebases. An index build raced by a delete, an update, or a compaction of fragments it does not cover re-builds the whole index; Lance publishes it on top. Same for a compaction raced by a delete on other fragments, and a delete raced by a delete on other fragments.

    After this task every pair is decided by Lance 12's rules (TransactionRebase::check_txn and its check_*_txn functions): compatible pairs are rebased (C2, C3) without re-running, incompatible ones fail with Lance's message and are not re-run, retryable ones keep today's behaviour (re-run by retry_on_conflict, up to its limit -- a deliberate, documented difference: pylance surfaces some of them to the user, nanolance retries them itself, with the same end state a user retry gives).

    The pylance "ok" rows above can be internal re-runs (pylance's own delete / update retry); the row counts are what must match. The wording to use (Lance's retryable_conflict_err / incompatible_conflict_err, conflict_resolver.rs ~line 229):

    • incompatible: Incompatible transaction: This {Ours} transaction is incompatible with concurrent transaction {Theirs} at version {v}. -- through Python an OSError (not CommitConflictError); through lance-c the error code pylance's maps to (see src/api/lance_c.cpp ~line 202, which already maps "commit conflict").
    • retryable: keep nanolance's commit conflict: ... prefix (that is what retry_on_conflict and src/api/lance_c.cpp key on), followed by Lance's text Retryable commit conflict for version {v}: This {Ours} transaction was preempted by concurrent transaction {Theirs} at version {v}. Please retry. -- seen only when the retries run out, or by operations that do not retry.

    {Ours} / {Theirs} are Lance's operation names (Append, Delete, Overwrite, CreateIndex, Rewrite, Merge, Restore, ReserveFragments, Update, Project, UpdateConfig, DataReplacement, DataOverlay, Clone, UpdateBases).

    3. Where things are in nanolance¶

    • src/dataset/dataset.cpp: rebase (~92), commit_next_version (~182; the retry loop ~227).
    • What a commit is, as Lance's transaction: derive_transaction_operation(parent, next) (src/table/transaction_file.hpp) -- the same derivation that writes _transactions/*.txn on every commit. The other writers' transactions: each intervening manifest's transaction_file (_transactions/<name>), written by nanolance and by pylance alike. A version with no transaction file (old datasets) is a retryable conflict (today's behaviour).
    • Decoding and applying a transaction: src/table/dataset_transaction.cpp -- decode_operation (~295), struct Operation (~259), apply_operation(base, op, next, ...) (~847), used by the Python LanceDataset.commit path. Move what you need into an internal header (src/table/dataset_transaction_ops.hpp or similar); do not duplicate the decoder.
    • The Python transaction API's own port of the matrix: bindings/python/nanolance/lance/_transactions.py conflict_with (~1002). It covers hand-built transactions without affected rows; the C++ port must agree with it on every pair it covers (a test asserts this for the pairs both can express). Do not change the Python commit path in this task.
    • Re-run wrappers: grep -n "retry_on_conflict" src/*.cpp src/*.hpp (delete, update, merge_insert, compaction, optimize_indices). Index builds (src/index/scalar/scalar_index.cpp ~1882 / ~2127, src/index/vector/vector_index_build.cpp ~2187, src/index/fts/fts_index_build.cpp ~955, src/dataset/index_segments.cpp ~397) call commit_next_version directly.

    4. Phases¶

    • C1 (classify). On a lost race, for each version v in (read version, latest]: decode its transaction, decide ours-vs-theirs with a C++ port of check_txn (the check_*_txn functions for the operations nanolance's C++ commits: Append, Delete, Update, Overwrite, CreateIndex, Rewrite, Merge, Project, UpdateConfig, Restore, ReserveFragments, DataReplacement, DataOverlay, Clone, UpdateBases; the MemWAL / FRI-only branches only where nanolance writes those). The first incompatible or retryable verdict decides. Incompatible: fail with the message in section 2, no re-run. Retryable: today's path. All compatible: today's rebase for now (C2 replaces it). The two "wrong" rows of section 2 then match pylance.
    • C2 (rebase). When every intervening transaction is compatible, build the new manifest by applying our operation to the latest manifest (apply_operation), with Lance's adjustments in finish / finish_create_index / finish_rewrite (conflict_resolver.rs ~1814, ~2082, ~2197): an index built from an older version keeps only the fragments still present (prune_updated_fields_from_indices for a concurrent Update of an indexed field), a rewrite's indexes remapped against the latest manifest, fragment ids after the latest max_fragment_id. rebase's append-only special case becomes one instance of this, or goes. Add an internal counter (C++ only, for tests: e.g. commit_conflict_stats() with rebased, retried, refused) so tests can tell a rebase from a re-run.
    • C3 (deletion vectors). Delete / Update against a concurrent Delete / Update on the same fragment with unchanged data files (check_delete_txn ~349, check_update_txn ~453, finish_delete_update ~1836): the delete / update passes the row addresses it deleted (its affected rows) to the commit; the commit reads the latest deletion file of each such fragment, conflicts (retryable, Lance's row-address message) if they overlap, else writes a merged deletion file (and removes a fragment whose rows are now all deleted, as Lance does). Without affected rows, retryable (as Lance).
