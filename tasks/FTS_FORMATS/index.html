    1. Facts (measured on pylance 12.0.0 here)¶

    nanolance today builds and reads format_version 2 only: posting blocks of 128 documents, posting_tail_codec = varint_delta_v1, positions in positions_layout = shared_stream_v2. Python refuses format_version, block_size, analyzer, split_identifiers, split_on_numerics, preserve_original, index_operators (_INVERTED_OPTIONS / _inverted_params, bindings/python/nanolance/lance/dataset.py ~1015); the native side refuses block size != 128 (src/index/fts/fts_index_build.cpp ~561); the reader refuses format != "2" and block != "128" (load_inverted, src/index/fts/fts_search.cpp ~716).

    Lance's rules (index/format.rs, tokenizer.rs): - format_version accepts 1 | 2 | 3 | "1" | "v1" | "V1" | ...; anything else -> ValueError unsupported FTS format version {v}, expected 1, 2, or 3. block_size is 128 or 256, else a ValueError naming block_size (copy Lance's invalid_block_size_message). - Default format: 2 with block 128, 3 with block 256, 3 with the code analyzer. format 1 / 2 with block 256 -> FTS format_version={1|2} is incompatible with block_size=256; use format_version=3. - The manifest index's index_version (what describe_indices()[i].segments[0].index_version shows) = the format version (1, 2 or 3). - Files are the same four (metadata.lance, part_N_{docs,invert,tokens}.lance) for every version. metadata.lance keys: format_version, partitions, params, posting_block_size, posting_tail_codec, token_set_format = fst, plus positions_layout / positions_codec only when with_position and format >= 2. invert.lance's schema metadata repeats format_version, posting_block_size and (format >= 2) posting_tail_codec. - V3 with block 128 is byte-identical to V2 except format_version = "3" (docs / tokens files equal, invert differs only in its metadata) -- verified. - V1 = posting_tail_codec = fixed32_v1 (tail block stores doc ids / frequencies as plain u32; nanolance's decoder already has TailCodec::Fixed32, src/index/fts/fts_posting.cpp ~111 -- but the reader looks for the string "fixed32", pylance writes "fixed32_v1": fix it). With with_position, V1 has no positions_layout: invert.lance has an extra column _position: list<list<large_binary>> -- per posting list, per document, a compressed position block (Lance: COMPRESSED_POSITION_COL / _position in index.rs / builder.rs; grep compress_positions\|POSITION_COL there). nanolance currently reports that layout as unsupported (positions_error); F1 reads and writes it. - Block 256 (encoding.rs 66-330): full blocks are BitPacker8x (8 lanes x 32, same scheme as the 4x one in src/index/fts/fts_posting.cpp, 8 interleaved lanes instead of 4): doc ids as a sorted block [u32 first doc][u8 bits][packed deltas], then frequencies patched FOR [u8 width][u8 exception count][packed body][exceptions: (u8 index, varint high bits)...] (compress_pfor_block_with -- copy its width choice exactly so bytes match). No 4-byte block max score prefix on any 256 block, including the remainder (posting_block_score_prefix_len). The tail (remainder < 256) uses the tail codec as today. Impact skip data (_impacts) uses the same entry encoding for every block size, one entry per posting block and one per 32 blocks (impact.rs top; nanolance's encode_impact_entry in src/index/fts/fts_index_build.cpp ~100-130). - Code analyzer (analyzer="code", or base_tokenizer="code"): params JSON written into params: "base_tokenizer":"code", "stem":false, "remove_stop_words":false, "lower_case":true, "ascii_folding":true, and four extra keys (nanolance already writes them, as false): "split_identifiers" (default false), "split_on_numerics" (default true), "preserve_original" (default true), "index_operators" (default false). Pipeline (tokenizer.rs ~1081): CodeLexTokenizer(index_operators) then, only if split_identifiers, WordDelimiterFilter(preserve_original, split_on_numerics), then the usual filters (lower case, ascii folding, max token length). Errors (copy the messages): flags without analyzer='code' -> code analyzer flags require analyzer='code'; code with format 1 / 2 -> base_tokenizer='code' requires FTS format_version=3, got 2; base_tokenizer='code' with analyzer='text' and the other two in RawInvertedIndexParams::resolve (~286-335). stats index_stats(...)["indices"][0]["params"] has no "analyzer" key, has the four flags. The index details proto (InvertedIndexDetails) carries a code_config for code indexes (tokenizer.rs ~420; find nanolance's writer with grep -n "InvertedIndexDetails" src/*.cpp) -- compare the manifest bytes with pylance's.
