    1. The idea (measured on pylance 12.0.0 here)¶

    A Lance IVF vector index is two files in _indices/<uuid>/: auxiliary.idx = the storage (per-row codes, _rowid + one column) and index.idx = the sub-index over each partition. Storage kinds: FLAT (flat: fixed_size_list<float>[d], metadata storage_metadata = ["{\"dim\":d}"]), PQ (__pq_code: fixed_size_list<uint8>[m], the codebook in a global buffer), SQ (__sq_code: fixed_size_list<uint8>[d], storage_metadata = ["{\"dim\":d,\"num_bits\":8,\"bounds\":{\"start\":..,\"end\":..}}"]). Sub-index kinds: FLAT (index.idx with zero rows, schema __flat_marker: uint64 not null, metadata lance:flat = ["","",...] one empty string per partition) and HNSW (__vector_id: uint32, __neighbors: list<uint32>, _distance: list<float>, metadata lance:hnsw = [ {entry_point, params, level_offsets}, ... ] per partition). Both files carry lance:ivf (a global buffer index of the IVF model) and distance_type; index.idx carries lance:index = {"type": "<NAME>", "distance_type": ..}. Manifest details_type_url = /lance.index.pb.VectorIndexDetails for all of them.

    nanolance already reads, searches and builds three of the six pairings:

    name storage sub-index in nanolance
    IVF_FLAT FLAT FLAT yes
    IVF_PQ PQ FLAT yes
    IVF_HNSW_SQ SQ HNSW yes
    IVF_SQ SQ FLAT this task
    IVF_HNSW_PQ PQ HNSW this task
    IVF_HNSW_FLAT FLAT HNSW this task

    Measured examples (2000 x 16 float32, 4 partitions): IVF_SQ auxiliary.idx 35737 bytes, identical in layout to IVF_HNSW_SQ's; its index.idx 592 bytes, 0 rows, 2 global buffers. IVF_HNSW_PQ: PQ auxiliary.idx (2000 rows, storage_metadata with codebook_position, nbits, num_sub_vectors, dimension, transposed...) + HNSW index.idx exactly like IVF_HNSW_SQ's. IVF_HNSW_FLAT: FLAT auxiliary.idx (as IVF_FLAT's storage) + HNSW index.idx.

    So the work is to decouple storage from sub-index where the code assumes the three known pairs: find them with grep -n "IVF_HNSW_SQ\|IVF_PQ\|IVF_FLAT\|hnsw\|__sq_code\|__pq_code\|__flat_marker" src/index/vector/vector_search.cpp src/index/vector/vector_index_build.cpp include/nanolance/vector*.hpp, and the Python names that refuse these kinds (grep -n "IVF_SQ\|HNSW_PQ\|HNSW_FLAT\|does not support .* indexes" bindings/python/nanolance/lance/*.py). Reuse the SQ / PQ / FLAT distance code and the HNSW graph build / search that exist -- do not write new ones. Build parameters (num_bits, m, ef_construction, max_level, num_sub_vectors...) as pylance takes them; defaults as pylance's. Before writing a builder, build the same index with pylance and with nanolance on the same data and compare: schema, metadata keys, row counts, and that each engine's search over the other's index returns the same top-k (with nprobes = all partitions and a large ef, results must match exactly).
