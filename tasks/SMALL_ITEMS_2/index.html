    Task: small items bundle 2 -- API gaps of 2-9 pylance tests each¶

    Status: delegated (implementer: Claude Haiku 5.5, reviewer: Claude Opus 5.5). Three phases, each a fresh session: A types and validation, B plans and stats, C dataset / fragment APIs. ~55 of pylance's tests. Each item is independent: do them in the listed order, and report the ones you could not finish rather than stretching the session.

    0. Context budget¶

    About 100k tokens per session. grep -n then sed -n windows of at most ~120 lines; never read bindings/python/nanolance/lance/dataset.py (3.6k+), src/expr.cpp, src/lance_table_reader.cpp, src/index_search.cpp or bindings/python/src/nanolance_bindings.cpp whole. Cut all output. For each item: read the named pylance tests (.deps/pylance-tests/v12.0.0/tests/...), measure the behaviour on real pylance 12.0.0 (import lance in plain python3), then implement. Write nanolance's own code.

    Performance review (2026-10-16, reviewer), late materialization. Benchmarked against the build before this stretch (e9bf014): scalar-index queries over all columns were up to 3.7x slower (cat = 'c7', 100k of 5M rows: 45 -> 166 ms). Cause: the B2 default (Lance's heuristic: late for columns of 10+ bytes). Measured on nanolance, late (filter columns first, then a take by address) loses to its own scan: 1.17x slower at 0.005% selectivity on 2 KB strings, 0.88x at 1%, ~3x at 10% and more, ~2x on mixed columns. Decision: the default (late_materialization=None) reads early -- nanolance's own choice, its plan says so; an explicit True / column list still reads late (now through a direct take of the scan's sorted addresses: no Python sort, no list round trip). pylance's test_dataset.py::test_late_materialization_param asserts pylance's default plan and leaves the expected list (1172 -> 1171) on purpose: the plan must describe what runs.
