## What the numbers say

- **Numbers, dates and times: 2.5–3.5× faster.** On integer, float, boolean, timestamp, date and decimal columns nanolance's single-threaded reader beats Rust Lance on all four cores by 3.5× (numbers) and 2.5× (temporal), geometric mean; a 2M-row int64 id column reads in 6.0 ms against 17.6 ms. Writes are 2.2–2.8× faster. Files are the same size as Rust Lance's, within 2%.
- **Strings: 2× faster per core, level on all cores.** Against Rust Lance on one core, nanolance reads strings 2.1× faster; against Rust on all four cores it is 1.14× faster, from one thread. Writes are at parity (1.07–1.11×). FSST makes the files up to 11% smaller than Rust's (URLs: 7.8 vs 8.8 MB). Binary writes are the exception: 68 ms against Rust's 46 ms.
- **Nested data is where Rust leads.** Lists, maps and lists of structs: nanolance reads at 0.96× Rust on one core and 0.61× Rust on four (a map<string, int64> column: 50 ms against 23 ms), and writes at 0.92× and 0.76×. Vectors read faster than Rust on all cores (35 vs 47 ms) and plain structs faster than Rust on one core. The time goes to reassembling repetition and definition levels page by page, the next thing to optimize.
- **One thread, on purpose.** nanolance never starts a thread, which is what embedded and edge deployments want: predictable CPU, no pool to size, memory bounded by the writer's byte budget. That is why both Rust columns are shown: one core is the per-core comparison, all cores is out of the box. Across the 27 data types nanolance is faster than one-core Rust on 22 reads and 17 writes, and faster than four-core Rust on 18 reads and 18 writes.
- **Every file read by the other side, 81 of 81.** Rust Lance read every file nanolance wrote, and nanolance read every file Rust Lance wrote, from C++ and Python, each checked value by value before it was timed. Rust reads nanolance's files at 1.07× the time of its own (geometric mean). Building this benchmark found and fixed two problems: Rust read nanolance's integer columns 5.7× slower than its own (pages were too small), and nanolance refused Rust files whose pages switch encoding midway.
- **Python costs nothing.** The Python bindings hand Arrow buffers across without copying (the PyCapsule interface), so nanolance from Python reads and writes within noise of the C++ API (0.97× and 0.95× of its time, geometric mean), including conversion to a pyarrow.Table.
- **Parquet: 2× slower, sometimes smaller.** pyarrow's Parquet reader and writer, using all four cores, take 2.2× and 2.3× nanolance's time (geometric mean). Parquet's files are smaller for sorted or low-range numbers, where its delta and dictionary encodings apply (monotonic ids 0.46×, timestamps 0.37×, decimals 0.30× of Lance's size); both Lance writers produce the same, larger files there.
- **Known gaps, stated plainly.** Rust on one core reads booleans 1.8× faster (5.5 vs 10.0 ms) and writes them 2.6× faster. nanolance reads Rust's FullZip pages (128-dim vectors, long strings) about 3× slower than its own layout of the same data. With glibc's default allocator a large read pays for page faults; a retaining allocator (jemalloc, mimalloc, or two glibc environment variables) gives nanolance another 1.15× on average, which the full table shows.

## Method

- Machine: Intel Xeon @ 2.80 GHz, 4 cores, 16 GB, Linux 6.18. Rust Lance is pylance 12.0.0 writing and reading Lance file format 2.2; pyarrow 25.0.1; nanolance built Release at the commit shown above.
- 27 data types, 50,000 to 2,000,000 rows each (tens of MB in memory), one column per data type except the 10-column event table. Every writer receives the same input: the table as 64K-row Arrow batches.
- Every time is the median of 7 runs after one warm-up, with the files in the page cache: the warm, repeated read a query service sees.
- nanolance C++ runs pinned to one core, timed inside one process by tools/nlbench: a read is lance_table_read_dataset into Arrow arrays; a write is writer open, write_batch per batch, commit. glibc's default allocator unless a column says otherwise.
- Rust Lance runs twice: lance.dataset(path).to_table() and lance.write_dataset(...) with its default thread pools on all 4 cores, and in a separate process pinned to one core with LANCE_CPU_THREADS=1 and LANCE_IO_THREADS=1.
- Python times (nanolance.read_table / write_table) include conversion to and from pyarrow.Table. Parquet is pyarrow.parquet with zstd on all cores, as a familiar yardstick.
- Before any read was timed, its result was compared with the source table (values and types). A reader that returned anything else would be listed as a failure, not a time; this run had none.
