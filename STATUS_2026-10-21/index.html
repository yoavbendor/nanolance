    Status, 2026-10-21 (end of the Wave 3 run)¶

    Where we are¶

    • pylance compatibility: all 1242 expected pylance 12.0.0 tests pass against nanolance.lance; ctest 68/68; the bindings suite passes (3976 passed, 21 skipped, 1 xfailed, with the moto object-store tests on).
    • Wave 2 is done: S3 reads, IVF_RQ, branches and clones, Lance's conflict rules (rebase / retry / refuse), IVF_FLAT on binary vectors (Hamming).
    • Wave 3 so far:
    • Item 8, object-store writes (W1-W4): every write works on s3:// except the two listed below. That covers create, append and overwrite; delete, update and merge_insert; schema changes and compaction; every index build and optimize_indices; restore, config and metadata; tags, branches, clones and drop.
    • Manifests are published with a create-only PUT, as Lance does.
    • Extras beyond Lance:
      • A lost reply to the manifest PUT is recognised as our own commit, so no duplicate append is made.
      • A store that ignores If-None-Match is detected and refused, where Lance would silently lose commits.
    • Item 10: INVERTED indexes on nested fields. T5: the inline transaction (manifest field 21), migrate_manifest_paths_v2.
    • CI: a wasm build (-Oz, -Werror, a 512 KB gzip budget, a browser test), so the wasm target cannot rot silently. nanos3reader now has a static build tested on vanilla images.

    Found today, and worth knowing¶

    1. Fixed: objects over 8 MiB were uploaded as 0 bytes.
    2. Cause: in the S3 sink's spill path, finish() closed the temp file and spilled() then answered "no", so the empty memory buffer was sent instead of the file.
    3. The commit still succeeded, so a large write to S3 silently produced unreadable data files.
    4. Every moto test used small data, so none caught it. tools/s3_real_check.py --large did.
    5. A regression test now writes a 17 MB file.
    6. Fixed: packed and dedicated blobs (not inline) could not be read from S3. The read used std::ifstream; it now goes through io::ByteSource.
    7. Cleanup on S3 is not done (above). The W4 brief included it; the work stopped before it.
    8. Small differences from pylance, recorded and not changed:
    9. enable_v2_manifest_paths=False is ignored (nanolance always writes V2 names).
    10. S3 write bytes are not counted in the work stats.
    11. nanos3reader has no batch DELETE, so drop and cleanup send one request per object.
    12. Rows tied on a score can come back in a different order.
    13. Plan text differs from pylance's.
    14. A flaky test: test_vector_model_kept_or_retrained (shapes (3,16) vs (4,16)) failed once in CI and is noted in the ROADMAP.
    15. The Rust question:
    16. A Rust port would bring memory safety and keep wasm.
    17. The small binary comes from nanolance's own design choices, not from C++, so a port must keep the same choices: no tokio, no DataFusion, no arrow-rs compute kernels.
    18. Otherwise it ends up as large as pylance.

    Performance¶

    Speed-ups of nanolance; above 1.0x means nanolance is faster.

    vs Rust Lance (CI, 2026-10-20, AMD EPYC 9V74, 4 cores, same data, same parameters):

    Area Build Query / search
    BTREE ~2x scalar queries 1.2x-13.5x
    BITMAP 3.9x (as above)
    LABEL_LIST 2.6x (as above)
    IVF_FLAT 0.95x 1.6x-3.2x
    IVF_PQ 1.9x 3.1x-3.9x (recall 0.478 vs 0.480)
    IVF_HNSW_SQ 1.02x 3.4x-5.3x (recall 0.977 vs 0.976)
    FTS (INVERTED) 1.37x 6.8x-19x

    File format (CI, 2026-10-04, 27 datasets; the nested-write gains made since then are not included):

    • Writes: geomean C++ 1.92x faster than Rust, Python 1.78x.
    • Reads: geomean C++ 2.20x, Python 2.68x.
    • Slower than Rust:
    • writes of struct_mixed, mixed_events and binary_blobs (0.67x-0.90x);
    • reads of list_string and map (0.75x-0.79x).

    These are the targets of backlog #84.

    vs pylance (Python API to Python API, ROADMAP summary):

    • vector search 3.8x;
    • FTS 3.0x;
    • scalar queries 2.3x;
    • index builds 1.2x-3.8x;
    • reads 3.5x;
    • writes 1.9x.

    Footprint: the Python native library is 4.3 MB; pylance is 213 MB.

    Not measured yet: S3 upload throughput vs pylance (W5), for example streaming multipart from memory and parallel part uploads.

    Testing on real S3: tools/s3_real_check.py¶

    pip install pyarrow nanolance pylance      # pylance optional: enables the cross-engine checks
export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... AWS_REGION=...   # or AWS_PROFILE
python3 tools/s3_real_check.py s3://your-bucket/scratch/nanolance --large --faults
# S3-compatible store: add --endpoint https://... (and --allow-http for plain http)
    • 21 checks, each under its own fresh sub-prefix. It prints PASS / FAIL / SKIP per check and writes a JSON report (--report).
    • It deletes what it wrote unless --keep is given, and exits 1 if any check fails.
    • Credentials come only from the AWS chain and are never written to the report.
    • Expected today, from a run against moto:
    • 20 PASS;
    • cleanup_old_versions FAIL (refused on S3, the known gap above).
    • On real AWS, also look at:
    • racing_writers, which exercises If-None-Match on the real service;
    • lost_reply_of_manifest_put;
    • the timings, since moto is local and much faster than S3.
