    Browser: the weblance demo (shipped 2026-10-17)¶

    • Live demo: https://github.com/yoavbendor/weblance (public; GitHub Pages from main, root): a map of 25,000 COCO images by their SigLIP2 embeddings; a click fetches the 12 nearest rows' captions and JPEGs live from jrmiller/coco-2017-siglip2-embeddings on Hugging Face (one 48 GB Lance data file) with HTTP Range requests, through nanolance compiled to WebAssembly (433 KB gzipped) in six Web Workers. Verified in headless Chromium against the real dataset: 12 images, 3.66 MB fetched (0.008% of the file). The weblance repo holds only the built module, the page, the map data (tools/make_map.py rebuilds it) and the license notices; nanolance stays private.
    • How: every READ path goes through io::ByteSource (include/nanolance/byte_source.hpp): data files (pread, cached file end, coalesced column metadata, small-read block), manifests and version discovery, deletion files, tags, index-segment checks. wasm/weblance_glue.cpp registers an https source (synchronous XHR in a worker, single-range Range headers -- no CORS preflight -- with the redirected CDN URL cached per file) and a Hugging Face tree-API lister; wasm/build_weblance.sh builds the module; tests/test_byte_source_remote.cpp reads a dataset through a mem:// store after deleting the local directory. The I/O rework measured level or faster natively (wide scans 2x, takes 15-37%, a stat storm of ~800 stats per take removed).

    Performance¶

    Re-run 2026-10-17 on this 4-core container (bench/results/*.json, docs/BENCHMARKS.md, bench/results/report.html). Ratios are the other engine's time over nanolance's: above 1 means nanolance is faster. "1c" pins both to one core; "mt" is all cores; "py" is through Python (nanolance.lance against pylance).

    Against Rust Lance, 27 data types (geometric means):

    1 core all cores Python
    write 1.45x 1.71x 1.86x
    read (files written by Rust) 1.84x 3.78x 3.34x

    Against pylance, indexes (geometric means): scalar index builds and queries 2.09x, vector indexes 2.86x (IVF_FLAT, IVF_PQ, IVF_HNSW_SQ; recall equal), full-text 2.61x.

    list 1.20 0.66 1.08 same nested-write path
    list 0.78 0.94 0.63 nested write and read

    vector_f32x128 0.94 1.17 1.35
    bool_flags 0.78 2.14 5.05 single-core boolean write
    string_lowcard 1.40 1.00 0.99
    BTREE build on numeric columns -- 0.85-0.90 (pylance) -- bimodal run to run: 0.95 s or 1.45 s (pylance steady 1.2-1.3 s); find the slow mode

    Checked against older builds, so the numbers above are not regressions. Today's ratios are lower than the committed 26 September run (single-core reads 3.7x then, 1.8x now), but Rust itself is ~1.4x slower on this machine today, and the 26 September build (f852c5a, worktree /home/user/nl-baseline) and today's measure the same on the same machine: int64 / float64 / string reads within noise, long-string writes level. Two things to measure properly: small-column single-core writes look ~1-2 ms slower than on 26 September (8-11 ms vs 6-9 ms for 2M int32; likely the per-commit transaction file, which Lance writes too), and a full-text change this week was A/B-timed level. Benchmark on a quiet machine before and after each optimization; compare engines within one run (ratios), never across days.

    How to work (what worked this week)¶

    • One Haiku session per item, with pylance's behaviour measured first and written into its prompt or spec; a stop rule for anything touching shared planning code; Opus reviews the diff, re-runs the checks, answers questions, commits. Haiku sessions run ~100-200k tokens.
    • Review catches that mattered this week: a count memo keyed by filter only (stale after delete()), a reader path that silently returned a short dictionary column, __int128 breaking MSVC, a full-text change that needed an A/B timing to show it was not slower.
    • Run one full pytest at a time; two at once caused one spurious failure.
