# table: what a version is -- manifest, fragments, deletions, row ids, transactions, refs, index metadata

Used by: [scan](../scan/README.md), [index](../index/README.md), [dataset](../dataset/README.md), [api](../api/README.md). See [docs/LAYERS.md](../../docs/LAYERS.md).

Example: [examples/layers/table.cpp](../../examples/layers/table.cpp) (run with ctest -R nano_lance_example_table).

This layer reads and writes the Lance table format around the data files: the manifest of each version
(`_versions/`), its fragments and their data and deletion files, base paths, row id and row version
sequences, data overlays, the transaction of each commit (`_transactions/`) and the conflict verdicts
between concurrent ones, tags, branches, clones and cleanup (`_refs/`, `tree/`), and the metadata of
indices including the two system indices (fragment reuse, MemWAL). It does not read or write column data
(the file and encoding layers do), plan or run user operations such as delete, update, merge_insert or
compaction (the dataset layer does, committing through this layer), or build and search indices (the index
layer). It uses base, io, arrow (schema mapping), encoding and file.

## Using it

- Reading a version: `load_latest_manifest`, `load_manifest_version`, `list_manifest_versions`
  (`nanolance/manifest_reader.hpp`). They check the feature flags as Lance 12 does and fail with pylance's
  message on a bit this build does not know. A fragment's deletions: `read_manifest_deletion_vector`
  (`nanolance/deletion_vector.hpp`); where a file lives: `data_file_dir`, `deletion_file_dir`, `index_dir_of`
  (`nanolance/base_paths.hpp`); row ids and versions: `RowIdSequence`, `RowVersionSequence`,
  `read_fragment_row_meta`, `RowIdIndex`, `resolve_row_ids` (`nanolance/row_ids.hpp`); overlays:
  `read_fragment_overlays` (`nanolance/overlays.hpp`).
- Writing a version: `commit_dataset_version` (create, append, overwrite of freshly written data files) or
  `publish_manifest` for a manifest the caller built (`nanolance/manifest_writer.hpp`). `publish_manifest`
  writes the transaction file, then the manifest with put-if-absent; when another writer took the version
  it fails with an error starting `commit conflict` and leaves nothing behind. It does not rebase: the
  dataset layer's `commit_next_version` (`nanolance/dataset_commit.hpp`, defined in `src/dataset/`) is the
  commit loop that classifies the concurrent transactions (`check_txn`) and rebases (`rebase_operation`).
  Mutations should go through it, never call `publish_manifest` on a manifest read at an older version.
- Hand-built commits (pylance's `LanceDataset.commit`): `dataset_commit_hand_built`
  (`nanolance/dataset_transaction.hpp`) applies one encoded `lance.table.Transaction` operation to
  `base_version` and publishes `base_version + 1` exactly; it does not check what was committed since
  `read_version` (the caller does, with `commit_verdict`).
- Refs and housekeeping: `create_tag` / `create_branch` / `shallow_clone` / `deep_clone` /
  `cleanup_old_versions` / `drop_dataset` (`nanolance/dataset_refs.hpp`). Every commit runs the cleanup the
  dataset's `lance.auto_cleanup.*` config asks for (`run_auto_cleanup`).
- System indices: `FragReuse::load` and `fragment_reuse_index_entry` (`nanolance/frag_reuse.hpp`),
  `dataset_initialize_mem_wal` and `dataset_mem_wal_details` (`nanolance/mem_wal.hpp`). Index bookkeeping
  across commits: `retain_relevant_indices` and friends (`nanolance/index_maintenance.hpp`).
- The private headers (`table/dataset_operation.hpp`, `table/commit_conflicts.hpp`,
  `table/dataset_transaction_ops.hpp`, `table/transaction_file.hpp`, `table/index_location.hpp`) are for the
  dataset and index layers; include them by that path.
- Errors: every function returns `false` and sets `error`, with Lance's wording where pylance has one (tests
  compare them). Input read from disk is untrusted: decoders refuse malformed messages rather than guess.
  Functions keep no global state except the conflict counters of `dataset_commit.hpp`; concurrent writers
  are separated by put-if-absent on the manifest, not by locks.

## Modules

| module | what it holds | tests |
|---|---|---|
| `manifest_reader` | `_versions/` listing (V1, V2 and detached names), manifest framing, index section, feature-flag checks, inline transaction, V1-to-V2 rename | `nano_lance_manifest_writer`, `nano_lance_proto_roundtrip` |
| `manifest_writer` | manifest encoding and put-if-absent publish, create / append / overwrite commits, data file version checks | `nano_lance_manifest_writer` |
| `deletion_vector` | deletion files in both shapes (Arrow IPC offsets, portable roaring bitmap), read and write | `nano_lance_deletion_vector` |
| `row_ids` | RowIdSequence and RowDatasetVersionSequence codecs, fragment row meta, row id index, row id to address | `nano_lance_row_ids` |
| `base_paths` | BasePath messages, base_id of data, deletion and index files, the directory each resolves to, branch field | `nano_lance_base_paths` |
| `overlays` | DataOverlayFile coverage (dense, sparse), newest-wins, index staleness, appending overlays | `nano_lance_overlays` |
| `transaction_file` | the transaction of a commit: operation derived from the change, `_transactions/{read_version}-{uuid}.txn` | `nano_lance_transaction_file` |
| `dataset_operation` | decoder of every operation nanolance reads from a Transaction | `nano_lance_dataset_operation` |
| `dataset_transaction` | applying an operation to a manifest (Lance's build_manifest and validate), hand-built commits | `nano_lance_dataset_transaction` |
| `dataset_transaction_ops` | `rebase_operation`, the change re-applied on the latest version | `nano_lance_dataset_transaction_ops` |
| `commit_conflicts` | Lance 12's check_txn verdicts, with and without affected rows | `nano_lance_commit_conflicts` |
| `dataset_refs` | tags, branches, shallow and deep clones, cleanup, auto cleanup, drop | `nano_lance_dataset_refs` |
| `frag_reuse` | the `__lance_frag_reuse` index: address remapping, coverage remap, writing a new version entry | `nano_lance_frag_reuse` |
| `mem_wal` | the `__lance_mem_wal` index: initialize and read its details | `nano_lance_mem_wal` |
| `index_maintenance` | which indices and segments a commit keeps, coverage after compaction | `nano_lance_index_maintenance` |
| `index_location` | where an index's files go, dotted field paths, JSON index path | `nano_lance_index_location` |
| `dataset_commit` | (header only here) the commit loop's interface, defined in the dataset layer | `nano_lance_dataset_transaction_ops`, `nano_lance_commit_conflicts` |

## Known gaps

- Newer feature flags (bits 9-17) are refused rather than supported. The ones most likely to show up in
  pylance datasets soon are spilled row lineage (bit 11) and tagged fragment reuse transitions (bit 10);
  each needs reading a hidden column through the scan layer and a new FRI decoder respectively.
- The conflict checks have no arm for DataReplacement, DataOverlay or UpdateBases as the change being
  committed, and UpdateMemWalState is not decoded. These only make nanolance more conservative (a retry
  where Lance would rebase), except that UpdateMemWalState is retryable where the spec says incompatible.
  A few verdicts (Overwrite / UpdateConfig on the same key, Restore against an UpdateConfig of schema
  metadata) follow Lance 12, which the newer pages changed.
- The rebase does not re-stamp row ids on a stable-row-id dataset or accumulate fragment reuse indices:
  those commits retry instead, which costs time, not correctness.
- Inline transactions are read from field 21 only; field 23 (what newer Lance writes) is not read, so such a
  dataset falls back to the transaction file.
- Not implemented at all: external manifest stores, the version hint file, the fragment metadata tree,
  managed blobs, clustering metadata, fragment metadata maps, non-reusable field ids, primary keys, the
  `lance.compaction.*` config keys and the MemWAL write path. Datasets that rely on them are refused by the
  feature-flag checks where the spec gives them a flag; the others (version hint, compaction keys, primary
  key) are simply not used.
- Dense deletions are written as `.arrow` files rather than roaring bitmaps: valid, larger.
